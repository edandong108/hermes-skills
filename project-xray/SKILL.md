# 项目透视(Project X-Ray):企业级项目改造方法论

## Overview

接手一个企业级项目(改造/重构/接手老项目)时,最大的风险是"没看清就动手"。本技能定义一套**先透视、后动手**的流程:四个阶段,把项目的系统形态、内部组织、外部生存环境、接口与数据、代码规范、测试现状逐层看清,再决定改什么、怎么改。

**全局纪律(贯穿所有阶段)**:证据驱动,不臆造。只写能"从代码/配置/声明文件"证明的东西;没证据的宁可留空标"未验证",也不编。

## When to Use

- 接手一个不熟悉的代码仓库,需要快速建立全局认知
- 企业级项目改造/重构前的现状摸底
- 只需要其中一项产出(画架构图/接口清单/依赖梳理/测试摸底)
- 新成员 onboarding 一个复杂项目

**Don't use for:** 单文件小脚本、纯前端页面的小改动、已经非常熟悉的项目。

**阶段之间的依赖**:全流程时按序执行——阶段 1 的图是阶段 2 的导航;阶段 2 的接口/数据模型是阶段 4 测试摸底的输入;阶段 3 的规范最终落成 AGENTS.md/CLAUDE.md,供改造期 AI 编码遵循。单独调用某一阶段时,缺的前置资产(如 api-list.md)按需补齐或在产出中标注"基于部分信息"。

**图的输出风格**:三张图共享统一视觉规范(浅色主题/横向分带/白色圆角卡片/带端口标注/箭头带协议标签),样例图见 `assets/architecture-style-sample.png`,详见 phase1 文件末尾。

## Common Pitfalls(跨阶段)

1. **三张图混着画** — 架构图里塞满 Maven 模块,或依赖图里画内部调用。每张图只回答自己的那个问题。
2. **看完 README 就动手** — README 往往过时,必须结合 pom.xml / application.yml 交叉验证。
3. **基础设施画太细** — 日志、监控、配置在架构图里只值一个方框,展开是浪费注意力。
4. **忽略循环依赖** — 模块图的最大价值之一就是暴露循环依赖,画图时不检查等于白画。
5. **期待一轮出活** — 无论画图还是清单,第一版都必然有遗漏。方法论的核心是"产出→review→指出具体缺口→AI 迭代",而不是指望一次到位。

## Verification Checklist

每阶段完成后,对照该阶段文件末尾的"完成标准"逐项勾选。全流程完成时,四个阶段的 Checklist 全部通过。
