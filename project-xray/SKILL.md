# 项目透视(Project X-Ray):企业级项目改造方法论

## Overview

接手一个企业级项目(改造/重构/接手老项目)时,最大的风险是"没看清就动手"。本技能定义一套**先透视、后动手**的流程:第一步画三张图,把项目的系统形态、内部组织、外部生存环境全部看清,再决定改什么、怎么改。

三张图分别回答三个问题:
1. **架构图** — 这个项目长什么样?(系统级俯视)
2. **模块图** — 项目内部怎么组织?(代码级俯视)
3. **依赖图** — 项目靠什么外部能力活着?(生态级俯视)

## When to Use

- 接手一个不熟悉的代码仓库,需要快速建立全局认知
- 企业级项目改造/重构前的现状摸底
- 评估一个项目的技术风险和改造范围
- 新成员 onboarding 一个复杂项目

**Don't use for:** 单文件小脚本、纯前端页面的小改动、已经非常熟悉的项目。

## 第一阶段:画三张图

### (1) 架构图 — "这个项目长什么样"

**提示词(可直接用)**:

> 读一下这个仓库,为我画一张架构图。只基于真实代码、配置和声明文件,不要臆造模块、依赖或职责;找不到证据的,宁可留空并在说明里标注"未验证"。
>
> 第一步,明确范围与识别模块:
> - 按我指定的目录/模块(<scope>),各按技术栈解析其清单:Java/Maven → pom.xml(含父工程、dependencyManagement、模块聚合)与 src 分层;前端 → package.json(含 workspaces)与 src/api、路由、store 结构;Python → requirements/pyproject 与模块导入关系;其它 → 对应语言的包管理或源码结构。
> - 忽略构建产物与第三方缓存:node_modules、target/dist、本地包缓存、报告目录等。
> - 说明哪些仓库/服务属于本图范围,哪些只在说明里提一句边界,不要混进图里。
>
> 第二步,确定分层与粒度:
> - 按"端 / 前端 / 后端 / 数据 / 中间件"分带,但每个带内按职责拆模块,不要一个带只画一个框。
> - 后端至少体现 接入层(Controller) → 业务层(Service) → 持久层(Mapper/Repository),以及关键横切(鉴权、异常、日志)。
> - 每个模块标注"模块名 + 一句话职责"。
>
> 第三步,区分基础设施:
> - 承载主链路的依赖(从代码/配置能证明被调用:鉴权、缓存、注册/配置中心、消息、网关)必须独立成框,并标注是公司/云环境还是第三方;
> - 纯周边、不承载主链路的信息(日志、监控指标、国际化、静态资源等)合并成一个框概括即可。
>
> 第四步,画依赖关系:
> - 只画有证据的边,并注明来源(如前端 API 路径前缀、Feign/HTTP 调用、数据源 JDBC、服务注册发现、配置读取);无证据的边不要画。
> - 存在依赖环时用红色标注。
>
> 输出:
> - 指定格式与主题(默认 HTML 内嵌 SVG,可选 SVG / Mermaid / PPTX;浅色或深色)。
> - 保存到指定路径并给一张预览图;若可能,给出可复现的生成脚本或步骤。

**关键点**:
- **证据驱动,不臆造(第一原则)**:只画能"从代码/配置/声明文件"证明的东西。没证据的模块、依赖、职责宁可留空标"未验证",也不编一个像模像样的上去。架构图的错误比留白更危险。
- **分层要细,每模块一句话职责**:后端至少要拆出 接入层(Controller)→业务层(Service)→持久层(Mapper/Repository) 三层 + 横切(鉴权/异常/日志),不能一个"后端"框就完事。模块名配一句话职责,信息密度才够。
- **基础设施分主次**:承载主链路的(鉴权/缓存/注册中心/消息/网关)独立成框并标注归属;纯周边的(日志/监控/静态资源)一个框概括。别把两者同等对待。
- **边要有来源**:每条依赖线都注明证据(前端路径前缀/Feign调用/JDBC/服务注册/配置读取),无证据的边不画。

**常见坑**:
1. **臆造模块或依赖** — AI 会按"常识"补一个项目里根本不存在的模块,或画一条没证据的调用边。review 时逐条问"这条边/这个框的证据在哪",答不上来就删。
2. **一个带只画一个框** — 后端、前端各一个框,信息量为零。后端必须展开到三层 + 横切。
3. **漏掉 OpenTelemetry/可观测性链路** — observability 能力常通过 OTel 集成实现,架构图应体现"服务发出 trace → OTel Collector → 存储"这条链路。没画就直说"把 trace 链路补上"。
4. **指望一次画完美** — 画完说"放大 Server 层,把子模块调用关系画细一点""数据库层加上表名"。**迭代三五轮才能拿到能用的图,是常态**。

### (2) 模块图 — "项目内部怎么组织"

**提示词(可直接用)**:

> 看一下项目的 pom.xml,画一张内部模块依赖图。只画项目自己的模块,外部库不画。有循环依赖用红色标出来。

**关键点**:
- **强调"看 pom.xml"** — 多模块项目(parent pom + 各子模块 pom)的依赖关系都在 pom 里。不让 AI 读,它可能根据模块名瞎猜依赖方向。
- **"外部库不画"是必须的** — Spring Boot 一个项目的 transitive 依赖能到几百个,画进来就没法看。

**常见坑**:
1. **漏掉 start/入口模块** — start 模块通常是 entry point(main 方法在里面),AI 容易把它当"运行时入口"而非"代码模块"。review 时确认 start 在图里,且正确依赖其他 server 模块。
2. **依赖方向画反** — 典型正确方向:start 依赖 runtime 和 openapi,openapi 和 runtime 都依赖 core。出现 core 反过来依赖 runtime 就是错的,让 AI 重画。
3. **frontend 不应出现在这张图里** — 模块图只画 Java 模块的 Maven 依赖,frontend 是独立 React 工程,通过 HTTP 调用后端、不走 Maven。AI 塞进去就让它去掉。

### (3) 依赖图 — "项目靠什么外部能力活着"

**提示词(可直接用)**:

> 你是一名资深技术架构分析助手。请帮我分析下面指定项目的对外依赖,并按"三类"分色画出来、同时整理成一份 HTML 文档。
>
> ## 输入
> - 项目根目录或需要分析的代码目录范围(由我提供)。
> - 如果没有指定范围,默认分析整个仓库,但优先看构建配置、运行时配置和 README。
>
> ## 第一步:先解引用,不要套模板
> - 实际去读项目的构建文件、配置文件和 README,不要用示例项目的依赖清单填空。
> - 只列该项目真实存在的依赖,没出现的依赖不要写。
> - 每条依赖给一句"它在这里干什么",并标注证据来源文件(不写密钥、token、绝对路径)。
>
> ## 第二步:按技术栈找证据源
> - Java/Maven:读 pom.xml 的 dependencies / dependencyManagement,得到代码层 Java 依赖。
> - 前端/Node:读 package.json 的 dependencies / devDependencies,得到代码层前端依赖。
> - 运行时中间件:读 application.yml / properties / bootstrap 配置 / docker-compose.yml / 代码里的连接配置。
> - 外部 API:读 README、配置样例、.env,以及代码里对"外部域名 / 第三方 endpoint"的调用。
>
> ## 第三步:三类判定(灵魂,必须严格分色)
> 1. 关键代码依赖(蓝):会打进 jar 或装进 node_modules 的库/框架,证据来自 pom.xml 和 package.json。
> 2. 中间件(橙):运行时要连的服务(数据库、缓存、注册中心、配置中心、消息队列、可观测性采集器等),证据来自 yml/properties/docker-compose/代码配置。
> 3. 外部 API(红):项目依赖的第三方外部服务(模型服务、SSO/CAS、对象存储、第三方文档/网关等),证据来自 README/配置样例/代码里的外部域名或 endpoint。
>
> 判定口诀:
> - 既是 pom 里的"驱动/客户端"又有对应运行时"服务"的,要拆开:客户端进蓝,服务进橙。
> - 域名/endpoint 指向公司外或第三方服务 → 红。
> - 不要把中间件和外部 API 混为一类,不要把运行时服务和代码依赖混为一类。
>
> ## 第四步:输出
> 1. 一份同主题 HTML 文档,结构为三段卡片,含图例、来源说明和"本项目没有哪些常见依赖"的澄清。
> 2. 依赖多时按子模块分组(如"后端 Java / 前端 npm"),不编造。
>
> ## 硬约束 / 反模式
> - 禁止套用示例项目的依赖清单。
> - 禁止把 pom 依赖和运行时中间件并为一类。
> - 禁止把外部 API 归为中间件。
> - 禁止写死密钥、token、内网 IP、账号密码。
> - 优先可读性和分类正确,数量其次。

**关键点**:
- **先解引用,不套模板(第一原则)**:实际去读 pom.xml/package.json/yml/README,只列真实存在的依赖。没出现的依赖不要写——这是防"AI 拿示例项目清单填空"的命门。
- **三类严格分色,是这张图的灵魂**:蓝=代码依赖(打进jar/node_modules)、橙=运行时中间件(要连的服务)、红=外部 API(第三方 endpoint)。三类分开才能一眼分辨:哪些是代码层、哪些是运行时要连、哪些是外部第三方服务。
- **判定口诀**:pom 里的"客户端"与对应的运行时"服务"要拆开(客户端进蓝、服务进橙);域名指向公司外/第三方 → 红。不要把中间件和外部 API 混类。
- **安全红线**:不写密钥/token/内网IP/账号密码,证据只标来源文件名,不写绝对路径。

**常见坑**:
1. **套示例项目依赖清单** — AI 会拿"Spring Boot 标准项目"该有的依赖来填空,而不是读真实文件。review 时逐条问"这条依赖的证据文件在哪",答不上来就删。
2. **pom 依赖和运行时中间件混为一类** — MySQL 的 JDBC 驱动(蓝)和 MySQL 服务本身(橙)常被并成一类。按口诀拆开。
3. **外部 API 归成中间件** — 模型服务(如 DashScope)、SSO/CAS、对象存储是外部 API(红),不是中间件(橙)。
4. **transitive dependency 全列出来** — 一个 starter 拉几十个间接依赖,全画没法看。提示词强调"关键",review 时挑出主干依赖,砍掉无关的。
5. **外部模型 API 漏掉** — 它们通过配置注入,不在 pom.xml 里。让 AI 读 README 的 "Configure Your API Keys" 一节。
6. **泄密** — 把密钥/token/内网IP写进文档。产出前必须检查一遍,发现即删。

**三张图的统一输出风格(参考样例 assets/architecture-style-sample.png)**:

- **浅色主题**:浅灰底(#f1f2f5) + 白色圆角卡片;各带用低饱和马卡龙色区分(浅蓝 #e3f2fd / 浅绿 #e9f5e9 / 浅橙 #fff4e0 / 浅黄 #fafbe7)。
- **标题区**:主标题(「系统名 — 图类型」) + 一句话副标题定位(如 "Agent Studio · AI Agent lifecycle management platform")。
- **横向分带**:按 端/前端/后端/中间件/数据/外部API/运维 分带;每带标注技术栈注解(如 "React 18 + Ant Design 5" "Java 17 · Spring Boot 3.3 · port 8080")。
- **模块卡片**:白色圆角卡片,内部 = 模块名(粗体) + 多行小字要点(职责/关键类/子功能),一卡片一模块;后端多模块可各成一卡片并排。
- **中间件卡片**:服务名 + 端口(如 Nacos :8848、Redis :6379、OTel :4318) + 用途小字(Config center / Session cache / OTel collector)。
- **数据库卡片**:实例+端口(:3306) + 核心表清单内联小字。
- **边**:箭头带标签,标注协议与方向(如 HTTP/SSE、"push traces via OTLP · pull prompts via Nacos");依赖环红色。
- **图例**:颜色与线型语义放标题正下方,一眼看懂。

**三张图的完成标准**:
- [ ] 三张图全部产出(架构/模块/依赖)
- [ ] 架构图:分层清晰 + 每个模块一句话职责 + 前端合理展开 + 可观测链路在
- [ ] 模块图:只含自有 Java 模块 + 依赖方向经得起推敲 + start 模块在图里 + frontend 不在图里
- [ ] 依赖图:三类分色 + 只列关键依赖 + 中间件和外部 API 无遗漏
- [ ] 至少迭代过一轮("一次画完美"不存在)

## 第二阶段:梳理接口清单与 Schema

### (1) REST 接口清单 — "系统对外提供什么能力"

**提示词(可直接用)**:

> 扫一下这个项目里所有的 Controller,给我整理一份 REST 接口清单。每个接口列出方法(GET/POST 等)、路径、一句话说明、主要入参、返回结构。按模块分组。保存到 docs/api-list.md。

**关键点**:
- **按模块分组**是让清单有组织。分组的清单可读性远高于一张一百行的大表。
- **一句话说明**强制给出人类能看懂的意图,而不是只抄 @Operation 注解或方法名。接口叫 createPromptTemplate,说明应该是"创建一个新的 Prompt 模板",让非开发同事也能看懂。
- **主要入参、返回结构**只要主要的,不展开所有字段。字段细节交给数据模型那份文档。

**常见坑**:
1. **漏扫 Controller** — 多模块项目(如 server-core、server-openapi、server-runtime)Controller 分散各处。提示词里加一句"项目是多模块的,每个 server 子模块下都可能有 Controller"。第一版出来发现数量可疑,直接问"你扫了几个模块?有没有漏?",AI 会补回来。
2. **内部 RPC 与 REST 混在一起** — 有些是对外 REST,有些是给 SDK 或 Agent 用的内部接口。让清单区分"对外"和"内部"两类。
3. **返回结构写太粗** — "返回 Prompt 对象"不够。至少要说清"返回列表还是单个,有没有包装成 Result<> 这种统一响应结构"。不够就让它再细化一层。

### (2) 数据模型说明 — "系统的数据长什么样"

**提示词(可直接用)**:

> 看项目的 entity 类、DTO、数据库建表 SQL,给我梳理核心数据模型。每个模型列出字段、类型、一句话说明。标出主键、外键、枚举值。关键模型之间的关系画一张简单的 ER 图。

**关键点**:
- **三个数据源一起看**:entity(Java 层 model)、DTO(传输层 model)、建表 SQL(DB 层 model)。三者不完全一致是常态——entity 有的字段 DTO 不暴露,DTO 有的字段是两个 entity 的组合。让 AI 三边对照。
- **主键、外键、枚举值**是数据模型的硬信息:主键告诉你表怎么定位记录,外键告诉你表怎么关联,枚举告诉你字段取值范围(如 Prompt 状态、Experiment 运行状态)。这三个是改造时最容易踩坑的地方。
- **同时产出 Markdown 说明 + ER 图**:前者适合精确查找(PromptTemplate 表有哪些字段),后者适合整体把握(几个表怎么关联)。
- **ER 图必须是卡片式(dbdiagram.io/DrawSQL 风格),不要 Mermaid erDiagram 默认样式**:
  - 每个实体画成**表卡片**:表名栏(深色)+ 字段列表(字段名: 类型),主键加标识
  - **实线 = 外键关联,虚线 = 逻辑关联(无 FK 约束)**,线上标注基数(1:N / N:M)
  - 多 schema/多模块的实体用**分区分色**区分归属
  - 桥接表(如 reference)标注 N:M 桥接
  - 图例写在标题正下方(一眼看懂线型语义)
  - 布局实体错落排布,尽量避免关系线交叉
  - 实现方式优先:dbdiagram.io 的 DBML 语法(可直接导入)、或 Graphviz/Mermaid 定制样式,产出 SVG

**常见坑**:
1. **只看 entity 忽略建表 SQL** — 拿到的字段可能和数据库实际表不一致。JPA 的 @Transient 字段 entity 有、DB 没有;反过来 DB 有些字段没映射到 entity。**以 DB 层为准,entity 和 DTO 作为参照**。
2. **DTO 和 entity 混成一个说明** — 职责完全不同:entity 是持久层映射,DTO 是传输层契约。分开两份,分别说清楚。
3. **ER 图漏关系** — 有些关系不通过外键表达,是业务代码维护的"逻辑关联"(如 prompt_id 字段存在但 DB 没建外键约束)。除了看 DDL,也扫代码里 findBy 之类的查询方法,把隐式关系补上。

## 第三阶段:梳理代码风格、规范、约束

**目标**:让改造期新增/修改的代码与存量代码"长得一样",不产生风格分裂。存量代码的既有约定是最高优先级(Feathers 遗留代码第一原则)。

**三个层次,分开梳理(写混了就会晕)**:
- **代码风格(Style)** — 写出来长什么样:命名约定、分层模式、DTO 习惯、注释风格、格式化
- **代码规范(Conventions)** — 必须怎么做的规则:事务、异常、日志、参数校验、返回包装
- **代码约束(Constraints)** — 不能做什么:禁止的依赖、弃用模式、技术债红线、版本锁定

### (1) 代码风格 — "这个项目的代码长得什么样"

**提示词(可直接用)**:

> 抽样阅读这个项目核心模块的代表性代码文件,给我提取代码风格:类命名约定(Controller/Service/Repository 等后缀)、分层调用模式(Controller→Service→DAO 的典型链路)、DTO 使用习惯(何时建 DTO、何时直接传 entity)、注释风格(类注释/方法注释的覆盖程度和语言)、格式化约定(缩进、换行、导入排序)。输出一份"项目代码风格说明",每条规则配一个代码示例。

**关键点**:
- **抽样而非全量**:找核心业务链路 + 近期频繁修改的文件。全量读没意义,代表性文件才是风格的代表。
- **以实际代码为准,不是 README**:文档里写的规范可能没人遵守。git blame 最近的代码最接近团队当前真实风格。
- **每条规则配真实示例**:风格文档没有示例等于没说。"方法命名用动词开头"+"比如 getOrderById(而不是 findById)"才有约束力。

### (2) 代码规范 — "代码必须怎么做事"

**提示词(可直接用)**:

> 分析这个项目的代码,提取强制性的编码规范:事务管理方式(注解还是编程式?在 Service 层还是 DAO 层?)、异常处理模式(全局异常处理器?错误码体系?)、日志规范(用哪个 logger?什么级别打什么内容?)、参数校验方式(注解校验?手动校验?)、统一返回结构(Result<>?直接返回对象?)。逐条说明"这个项目是怎么做的",并指出违背示例(如果存在)。

**关键点**:
- **关注"横切模式"**:事务、异常、日志、校验是每个方法都会碰到的,它们的一致性直接决定代码库的健康度。
- **指出违背示例**:规范文档里写明"项目统一用 X,但下列文件违背了,改造时注意"——这就是改造的切入点。
- **检查配置文件**:checkstyle.xml、.editorconfig、.eslintrc、pom.xml 里的插件配置,是规范的可执行形态。

### (3) 代码约束 — "红线清单"

**提示词(可直接用)**:

> 梳理这个项目的代码约束(红线):1) 禁止事项——代码中被弃用/废弃的模式(@Deprecated 标记、TODO/FIXME 集中的区域、已知反模式);2) 依赖锁定——哪些库版本被强制锁定、为什么(历史事故?兼容性?);3) 技术债清单——哪些模块是公认的"雷区",改之前必须知道什么;4) 兼容性约束——对旧数据、旧接口、外部系统必须保持的行为。输出"项目红线清单"。

**关键点**:
- **约束是改造的"地雷图"**:改造最怕的就是踩到暗雷。红线清单就是探雷器。
- **版本锁定的原因比版本号重要**:"不能用 Spring 6 因为历史事故 X"比"Spring 5.3"更有价值。
- **最终形态是规则文件**:整个第三阶段的产出物,最终要落成项目根目录的 AGENTS.md / CLAUDE.md / .cursorrules,让 AI 编码时自动遵循。

**常见坑**:
1. **把"项目风格"和"业界最佳实践"混为一谈** — 改造要贴合项目现状,不是推广最佳实践。项目里就算用老式 try-catch,新代码也得跟着用,除非这是改造目标。
2. **只看核心代码,不看测试代码** — 测试的命名、结构、断言风格也是风格的一部分,而且是团队真实习惯的镜子。
3. **不按时间分层** — 2008 年的老代码和 2025 年的新代码风格可能完全不同。按 git 历史分层,以近期代码为准。
4. **产出物是纯散文文档** — 规范必须可执行:要么是 linter 配置,要么是代码搜索模式(如"搜 .*ServiceImpl 看命名"),要么是 AGENTS.md 规则。纯文档迟早被无视。

## 第四阶段:测试摸底(改造前先摸测试现状)

**目标**:回答"改造之前,至少要补哪几条测试,AI 才能放心地改"。注意——这个阶段**不是补测试**(那是改造启动后的事),是**摸清现状**:项目应该测什么、现在测了什么、缺口在哪里。

**核心思想(目标定义的反转)**:
> 老项目改造的目标**不是"达到 80% 覆盖率",是"改造路径上的关键节点都有兜底"**。

- 通用目标(覆盖率):AI 默认列 200 条"应该补的测试"(每个 controller 加单测、每个 service 加 mock),看起来都合理,但根本补不完,改造迟迟动不了。
- 改造目标(关键路径):聚焦、可控,把缺口收敛到可执行的 5-10 项 P0,让改造能启动。

摸底四步法,每步对应一份资产:
1. **摸核心链路**(应该测什么)
2. **摸现有测试**(现在测了什么)
3. **跑一遍看实际状态**(测试是否真的在跑、是否通过)
4. **算缺口清单**(关键链路 × 现有覆盖 → 缺口)

### Step 1:摸核心链路 — "应该测什么"

**提示词(可直接用)**:

> 基于 docs/api-list.md、docs/data-model.md、CLAUDE.md,给我列出这个项目最值得测的核心链路。要求:
> - 总数不超过 8 条,宁少勿多
> - 必须是"改造时容易出问题"的链路,不是所有链路
> - 每条写:链路名、起点(哪个接口)、关键节点(哪些 service / DB 操作)、终点(什么状态算成功)

**关键点**:
- **"关键路径 > 覆盖率"是这条的灵魂**:选的是"改造时容易出问题"的链路,不是"所有链路"。账号信息修改、Trace 列表分页这种边角不算核心;登录、核心业务创建与运行、数据集导入、批量执行、结果写入这种才算。
- **起点和终点必须明确到能直接转成测试断言**:不能含糊写"用户登录后做事",要写"POST /console/v1/auth/login → 校验密码 → 写入 Token → 返回 200 + accessToken"。明确的起终点 = 可执行断言。
- **依赖前面的资产**:核心链路基于 api-list(接口)、data-model(数据)、CLAUDE.md(规范)三者交叉得出,不是凭空想。

**review 重点**:
1. **是不是真核心** — 核心链路 = 改造最易出问题的关键业务流转,不是高频/常见操作。列了"账号信息修改"当核心链路,要让它重新选。
2. **起终点够不够明确** — 每条链路要能直接转成测试断言,含糊的"用户做某事"要打回重写。

**常见坑**:
1. **列成"所有链路清单"** — AI 容易把"重要"理解成"全面",一列列 20 条。掐死 ≤8 条,宁少勿多。
2. **起点终点含糊** — "用户登录后做事"这种不能转断言。要求每条链路写清接口路径 + 关键节点 + 成功状态。
3. **凭空选链路不参考资产** — 必须基于 api-list/data-model/CLAUDE.md 交叉得出,否则选出来的链路和真实系统对不上。

### Step 2-4(占位,待后续课程补全)

- Step 2 摸现有测试:梳理项目里已经有哪些测试(单测/集成/E2E),覆盖了哪些链路。
- Step 3 跑一遍看实际状态:现有测试是否真的在跑、是否通过、是否失效。
- Step 4 算缺口清单:核心链路 × 现有覆盖,算出"改造前至少要补哪几条 P0 测试"。

## Common Pitfalls(跨阶段)

1. **三张图混着画** — 架构图里塞满 Maven 模块,或依赖图里画内部调用。每张图只回答自己的那个问题。
2. **看完 README 就动手** — README 往往过时,必须结合 pom.xml / application.yml 交叉验证。
3. **基础设施画太细** — 日志、监控、配置在架构图里只值一个方框,展开是浪费注意力。
4. **忽略循环依赖** — 模块图的最大价值之一就是暴露循环依赖,画图时不检查等于白画。
5. **期待一轮出活** — 无论画图还是清单,第一版都必然有遗漏。方法论的核心是"产出→review→指出具体缺口→AI 迭代",而不是指望一次到位。
