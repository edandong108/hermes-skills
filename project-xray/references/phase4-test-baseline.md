# 第四阶段:测试摸底(改造前先摸测试现状)

**目标**:回答"改造之前,至少要补哪几条测试,AI 才能放心地改"。注意——这个阶段**不是补测试**(那是改造启动后的事),是**摸清现状**:项目应该测什么、现在测了什么、缺口在哪里。

**核心思想(目标定义的反转)**:
> 老项目改造的目标**不是"达到 80% 覆盖率",是"改造路径上的关键节点都有兜底"**。

- 通用目标(覆盖率):AI 默认列 200 条"应该补的测试"(每个 controller 加单测、每个 service 加 mock),看起来都合理,但根本补不完,改造迟迟动不了。
- 改造目标(关键路径):聚焦、可控,把缺口收敛到可执行的 5-10 项 P0,让改造能启动。

摸底四步法,每步对应一份资产:
1. **摸核心链路**(应该测什么)
2. **摸现有测试**(现在测了什么)
3. **跑一遍看实际状态**(测试是否真的在跑、是否通过)
4. **算缺口清单**(关键链路 × 现有覆盖 → 缺口)

## Step 1:摸核心链路 — "应该测什么"

**提示词(可直接用)**:

> 基于 docs/api-list.md、docs/data-model.md、CLAUDE.md,给我列出这个项目最值得测的核心链路。要求:
> - 总数不超过 8 条,宁少勿多
> - 必须是"改造时容易出问题"的链路,不是所有链路
> - 每条写:链路名、起点(哪个接口)、关键节点(哪些 service / DB 操作)、终点(什么状态算成功)

**关键点**:
- **"关键路径 > 覆盖率"是这条的灵魂**:选的是"改造时容易出问题"的链路,不是"所有链路"。账号信息修改、Trace 列表分页这种边角不算核心;登录、核心业务创建与运行、数据集导入、批量执行、结果写入这种才算。
- **起点和终点必须明确到能直接转成测试断言**:不能含糊写"用户登录后做事",要写"POST /console/v1/auth/login → 校验密码 → 写入 Token → 返回 200 + accessToken"。明确的起终点 = 可执行断言。
- **依赖前面的资产**:核心链路基于 api-list(接口)、data-model(数据)、CLAUDE.md(规范)三者交叉得出,不是凭空想。

**review 重点**:
1. **是不是真核心** — 核心链路 = 改造最易出问题的关键业务流转,不是高频/常见操作。列了"账号信息修改"当核心链路,要让它重新选。
2. **起终点够不够明确** — 每条链路要能直接转成测试断言,含糊的"用户做某事"要打回重写。

**常见坑**:
1. **列成"所有链路清单"** — AI 容易把"重要"理解成"全面",一列列 20 条。掐死 ≤8 条,宁少勿多。
2. **起点终点含糊** — "用户登录后做事"这种不能转断言。要求每条链路写清接口路径 + 关键节点 + 成功状态。
3. **凭空选链路不参考资产** — 必须基于 api-list/data-model/CLAUDE.md 交叉得出,否则选出来的链路和真实系统对不上。

## Step 2-4(占位,待后续课程补全)

- Step 2 摸现有测试:梳理项目里已经有哪些测试(单测/集成/E2E),覆盖了哪些链路。
- Step 3 跑一遍看实际状态:现有测试是否真的在跑、是否通过、是否失效。
- Step 4 算缺口清单:核心链路 × 现有覆盖,算出"改造前至少要补哪几条 P0 测试"。

## 完成标准

- [ ] 核心链路 ≤8 条,是"改造易出问题"的链路,不是所有链路
- [ ] 每条链路写清 起点(接口) / 关键节点(service/DB) / 终点(成功状态)
- [ ] 起终点明确到能直接转成测试断言
- [ ] 核心链路基于 api-list / data-model / CLAUDE.md 交叉得出,不是凭空想
- [ ] 已把"覆盖率目标"换成"关键路径兜底目标",缺口收敛到 5-10 项 P0
